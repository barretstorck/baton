## What went right

- Every issue was finished in one day, with no review escalations and no replans. The two rounds of changes were one task each.
- Round 1 of the review of #136 caught a real regression: the new heredoc handling let a heredoc piped into a shell through unchecked. It was fixed in the same pull request.
- No agent grew past 250K tokens. The largest task agent peaked at 39K, so the one-task-per-agent rule held.
- The spike #133 measured friction instead of guessing. Over 58,708 replayed `Bash` commands, the current gate refuses 3,857, of which 1,325 are not publishes. The prototype refuses 251 (5 not publishes) and still catches the 3 private publishes.
- Checking the branch tip with `git ls-remote` caught a developer report with a made-up full sha (#131 task 3). Its short sha was right.

## What went wrong

| Problem | Cost | Root cause |
|---|---|---|
| #131 and #134 stayed held for "expected files overlap" after #135 had merged | About 2 of 4 slots in use for most of the sprint; #134 started only after #131 merged | `baton sprint-status` runs the installed plugin (0.5.1), not the repository's `main`. A merged change to Baton's own scheduling takes effect only after a plugin update and a session restart. |
| The publish gate refused harmless commands from the orchestrator and from nearly every developer: heredocs of Python, `cd <dir> && ...`, a heredoc body file written and posted in one command | Retries and split commands in most agents; the spike developer worked around three refusals | The gate under work was also the gate in force: the session ran 0.5.1, so #132's fixes did not apply to this sprint. The parsing design itself is what #133 recommends replacing (#139). |
| Automated security reviews flagged new gate bypasses after almost every commit on #136 (4 rounds, 12 findings) | Four orchestrator status comments; review time on #136; findings carried to #133 | Each parser rule added to refuse less opens new differentials with bash. This is the arms race #133 describes, and its design deletes the parser instead of extending it. |
| `baton pr create` fails from a detached HEAD | Three developers had to create a local branch by hand | The worktrees the developers start from are detached; `baton pr create` needs a named branch. |
| Every code pull request needed the maintainer's `/baton approve` | Three waits on the maintainer before a merge | All four code issues changed protected gate, hook or scan files. This is expected for this sprint's subject. |
| The orchestrator used 53% of the sprint's weighted tokens | 2.0M of 3.8M weighted | Many short passes, each one re-reading `sprint-status`, plus relaying the security-review findings. |

## How to improve

1. **Baton itself:** `baton pr create` should work from a detached HEAD, by taking the branch name from the issue or creating the branch.
2. **Baton itself:** say in the sprint skill that changes to Baton's own commands take effect only after a plugin update and a session restart. When a merged sprint issue changes `sprint-status`, the orchestrator can then tell the maintainer at once.
3. **Issue #139 and its follow-ups:** take the gate redesign from #133 forward; it is the root cause of most of the friction above. The order is set by #145 being `Blocked by: #139`. The rest is for the maintainer to rank.
4. **Baton itself:** an automated security review that keeps finding parser differentials is a signal to stop patching the parser. The sprint skill could route such findings to the open design issue instead of to the pull request.
