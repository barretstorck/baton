## What went right

- All 46 issues finished, with no carry-over, and every plan task was ticked by the developer that did it (177 tasks).
- The three spikes paid off: #222 and #229 each produced a set of follow-up issues that were then delivered in this sprint, and #228 settled most of the identity design before #177 started.
- Review caught real defects before merge. Round 2 of the review of #307 found that a typed `baton exec --role ...` skipped the private-content scan and accepted other hosts; both are fixed.
- Task agents stayed small: no task, refine, spike or review agent went above 250K tokens (peak 147K).
- Developers found stale plans early. #245 and #279 (twice) sent a REPLAN once the files they edit had moved, instead of editing the wrong place.

## What went wrong

| Problem | Cost | Root cause |
|---|---|---|
| The orchestrator sessions grew far past the 250K mark. | The three orchestrator sessions are the largest rows of the usage table, about 25M weighted tokens together, with an average context of 244K to 381K and 60% to 100% of calls above 250K. | The orchestrator runs one long session and the sprint skill it loads was large. #219, #249 (orchestrator as a background subagent), #273 (slimmer skill) and #247 (compaction reminder) landed during this sprint; the effect is not yet measured. |
| Protected-path pull requests waited for `/baton approve`. | Four approved pull requests (#281 through #284) sat for a long time and their dependents (#216, #243, #245, #251, #274, #279) were held. | Each protected-path pull request needs its own approval comment, and an issue only releases its dependents when its pull request merges to the default branch. |
| `baton merge-pr` can only merge to the default branch. | The request to collect the sprint into one pull request meant Baton stopped merging, and conflicts between approved branches had to be resolved by a separate assembly step that no reviewer saw. | Baton has no integration-branch mode; `merge-pr` refuses any other base. |
| Automated security notes arrived after most commits and were mostly guardrail-evasion variants. | About a dozen notes; `baton exec` alone drew five sets of notes and two review rounds, and two sets became backlog issues (#299 and #305). | The notes are produced per commit with no knowledge of the brief's `## Responsibilities`, so deliberate-evasion variants look the same as plain gaps. |
| Plans went stale while they waited. | #279's plan was written against a commit before the reference split and needed two REPLANs; #245's premise was stale after #244. | A plan is anchored to one commit and nothing re-anchors it when its blockers close and move the text. |

## How to improve

1. **Baton itself:** let `baton merge-pr` merge into a named integration branch, or provide a command that assembles approved pull requests into one combined pull request with its conflict list. Today the assembly is done by hand by an agent and is not reviewed.
2. **Baton itself:** one `/baton approve` on a combined pull request should cover the protected paths of its source pull requests, so a protected-path pull request does not hold its dependents.
3. **Baton itself:** re-anchor a plan (or hold it for re-refinement) when a blocker's merge moves the files the plan edits, so plans do not need a REPLAN.
4. **This repository's brief:** note that deliberate-evasion variants of gate checks are set aside, so a reviewer does not need the instruction each time (the reviewer already follows `## Responsibilities`). Needs the maintainer's approval because `.baton/` is protected.
5. **Issue:** decide whether `baton exec` needs a hard boundary at the point where the token is issued instead of the command line; recorded on #309 and left to the maintainer.
6. **Measurement:** compare the orchestrator's average context with a sprint that runs the new subagent orchestrator (#219, #249) and the slimmer skill (#273); the numbers above are the before.
