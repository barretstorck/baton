## What went wrong

| Problem | Cost | Root cause |
|---|---|---|
| #5 shipped, through tasks 1–9, code that trusted the `Plan:` link in an issue body. Its ref went to `git fetch` (argument injection), its path to file writes and `git rm` (path traversal), and its branch to `git push` (push to any branch, including `main`). Plan files were also written through symlinks. | One review round on #11: 3 fix tasks, 54 calls, 0.8M weighted. | The #5 plan did not treat the issue body as untrusted input, and no task said to validate the link. | #5's review-staleness rule excluded the whole `plans/` folder, so any change there after approval would merge without review. | A follow-up issue (#12) with 3 tasks and a second review. | The acceptance criterion ("removing the plan file does not void approval") was implemented at folder scope, the simplest form, rather than at the scope it asked for. |
| The refiner for #12 widened the exemption to any edit of the linked plan file, which contradicted the criteria it had just written. | One maintainer question and a plan replacement. | The refiner made a design choice to simplify the plan and recorded it only in its report, not on the issue. |
| Plan-only and verification-only tasks (#7 task 2, #4 task 4, #5 tasks 12–14, #12 task 3) returned `DONE` with an unchanged sha. | None, but the "tip must match" check cannot tell such a task from one that did nothing. | Verification-only tasks produce no commit. |
| The #5 develop skill gained a `--force-with-lease` exception for rebasing a plan-only branch. | The maintainer was asked; the reviewer judged it safe. | The new design rebases a plan-only branch onto the default branch, which makes the push a non-fast-forward. |

## How to improve

1. **Baton itself (refine skill):** when a plan reads anything from an issue body, a comment or a pull request and passes it to git, the shell or the filesystem, the plan must include a task that validates it, and its check must test hostile inputs. This would have caught the #5 findings before task 1.
2. **Baton itself (refine skill):** a refiner must not narrow or widen an acceptance criterion in its plan. If it wants to, it posts a question on the issue instead of noting it only in its report.
3. **Baton itself (sprint skill):** for a task whose `Check:` is verification only, accept `DONE <unchanged sha>` explicitly, so a no-op is not mistaken for a lost commit.
4. **Baton itself:** consider merging the default branch into a plan-only branch instead of rebasing it, which removes the need for the `--force-with-lease` exception added in #5.
