## Context

`baton install-hooks` (`lib/baton/githooks.py` `install()`) writes the absolute path of the plugin's `bin/baton` into the `pre-commit` and `pre-push` hooks. Plugin installs live in a versioned cache folder (`~/.claude/plugins/cache/baton/baton/<version>/`), so the path stops existing once old versions are pruned. Observed: the Baton clone's hooks still `exec` `.../0.3.0/bin/baton`, while only 0.4.0, 0.5.0 and 0.5.1 are cached.

`githooks.installed()` only looks for the `baton git-hook` tag line. The gate therefore keeps reporting the hooks as installed while they point at a missing file, and every commit in that clone fails with a shell "not found" error and no hint to re-run `baton install-hooks`.

The other findings of the original audit were split out: the gate's read-only false positives and refusal messages are #132, the forge-neutral gate design is the spike #133, and the private-terms warning and the fail-open note are #134.

## Diagnosis

- **Reproduced** with tests in a scratch worktree at f86c9cc. The hooks were installed with a `baton` path under a temporary `0.3.0/bin/` that does not exist. `githooks.installed(repo)` returned True (expected False), and `git commit` failed with `.git/hooks/pre-commit: exec: line 3: <path>/0.3.0/bin/baton: not found` (expected: the scans run, or a message naming `baton install-hooks`).
- **Cause:** `githooks.install()` (`lib/baton/githooks.py:230-245`) writes a hook that `exec`s one fixed absolute path with no fallback. `githooks.installed()` (`lib/baton/githooks.py:216-227`) checks only the tag line, never that the path exists. `gate.decide()` (`lib/baton/gate.py:562-563`) relies on `installed()`.
- **Not a regression:** the fixed path has been there since the hooks were added in 8e3266d.

## Acceptance criteria

- The hook that `baton install-hooks` writes runs the `baton` path it recorded when that file exists, else the `baton` found on `PATH`. When neither exists, it exits non-zero with a message on standard error that names `baton install-hooks`, never a bare shell "not found".
- `githooks.installed()` returns False when a hook's recorded `baton` path does not exist, for hooks written in the old format (`exec "<path>" git-hook ...`) and the new one. The gate then refuses `git commit` and `git push` with a message to run `baton install-hooks`.
- Tests in `tests/test_githooks.py` and `tests/test_gate.py` cover a hook whose target no longer exists: `installed()`, the PATH fallback, the message when there is no `baton` at all, and the gate's refusal.
- `README.md` and `skills/init/SKILL.md` say that the gate asks to re-run `baton install-hooks` after a plugin update removes the old version.
- `PYTHONPATH=lib python3 -m unittest discover -s tests` passes.

## Out of scope

- The gate's read-only false positives and refusal wording (#132).
- The forge-neutral gate design (#133).
- The private-terms warning and the fail-open note (#134).
- Weakening the privacy scan patterns or the `merge-pr` acceptance checks.

### Pattern

Hook script text is built in `githooks.install()` (`lib/baton/githooks.py:230-245`). Tests build throwaway repositories with `make_repo()` and `write()` in `tests/test_githooks.py:18-35` and `tests/test_gate.py:18-27`, and call real `git` there (no `FakeRunner` for hooks).

### Design notes

- The hook tries its recorded path first, so a repository keeps the `baton` version that installed it as long as that exists; `PATH` is only the fallback, for a person committing in a terminal after the plugin update.
- `installed()` treats a missing recorded path as "not installed" even when `PATH` would work. The gate then asks for a re-install, which pins the hooks to the current version again.
- A tagged hook with no recorded path (a hand-written stub) counts as not installed. `tests/test_gate.py` `make_repo()` writes such stubs today, so task 2 changes it to install real hooks.
